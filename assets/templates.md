```
二、核心痛点：（量化，如「每单人工审核 8 分钟，日 2000 单」）
三、功能需求：
  - Must-have（上线必需）：
    1.
  - Nice-to-have（后续迭代）：
    1.
四、非功能需求：
  - 性能（吞吐/延迟/并发）：
  - 安全（加密/权限/审计）：
  - 合规（数据出境/PIPL/行业监管）：
五、技术约束：（既有系统、网络、私有化要求、语言）
六、成功标准：（可量化，如「人工审核占比从 100% 降至 ≤30%」）

```

**补全需求反问清单（逐条确认）**
- [ ] 业务目标可量化？不可量化则要求客户给基线数字
- [ ] 当前谁做、怎么做的？耗时/成本/错误率基线是多少？
- [ ] 峰值与常态负载？
- [ ] 数据来源、是否可授权使用、是否含 PII？
- [ ] 失败的业务代价与兜底要求？
- [ ] 上线后谁运营、有无 IT 接口人？
- [ ] 决策人与预算是否明确？
- [ ] 是否有竞品已在做、客户满意度如何？

**架构决策默认值**
- 不确定性高的环节走 Human-in-the-Loop（预审 / 后置审批 / 抽检）
- 置信度路由：≥0.90 自动；0.70–0.90 人工复核；<0.70 人工处理；超时 30s 降级人工
- 跨服务集成必须带鉴权 + 指数退避重试 + Saga 补偿

## 5. POC 方案

```
## POC 方案
- POC 目标与成功标准：（量化，如「200 条样本上准确率 ≥85%，人工复核 ≤30%」）
- 测试场景设计：（2–4 个，覆盖常态与边界）
- 数据准备方案：（来源、规模、脱敏要求、客户提供时限）
- 环境搭建要求：（网络/算力/账号/接口人）
- 实施周期与里程碑：（建议 2–4 周）
- 验收标准：（指标 + 测量方法 + 谁认定通过）
- 风险预案：（数据不到位 / 指标不达标 / 客户无人力）
- 双方责任：我方 ____ ；客户方 ____ （签字）
```

**成功标准写法**：错「效果明显提升」→ 对「人工审核占比 100%→≤30%，单均 8min→≤2min」；错「准确率够用」→ 对「200 条标注样本 F1 ≥0.85，误杀率 ≤1%」。

**五大失败原因提前规避**：范围膨胀（用需求文档锁范围）/ 数据不到位（写时限与后果）/ 标准先松后紧（双方签字）/ 无业务基线（先跑一批基线）/ 客户无人配合（明确接口人 + 每周同步）。

## 6. 评测与验收报告

```
## 评测验收报告
1. 结论摘要：推荐 / 有条件推荐 / 不推荐
2. 精度对比表（现有 vs 新，附变化 pp）
3. 性能对比表（TTFT P50/P99、TPOT、吞吐，附变化 %）
4. 成本表（单 token 成本、GPU 张数变化）
5. 兼容性清单（框架/API/量化/硬件）
6. 风险（许可证/维护/精度）
7. 适用与不适用场景
8. 后续计划（灰度发布 或 记录不引入原因并定期复评）
```

**达标阈值（默认，可按场景调）**
- 精度：量化后关键 benchmark 损失 <2%（FP8 <0.5%、INT8 <0.5%、INT4 接受 1–3% 但需业务验证）
- 延迟：P99 TTFT <SLA（如 1s），TPOT <30ms 为流畅基准
- 吞吐：GPU 利用率 >70%、KV Cache 使用率 <90%、错误率 <0.1%
- 应用类：Context Recall ≥0.80、Faithfulness ≥0.85、任务完成率 ≥80%
- 稳定性：10 QPS 持续 24h 无显存泄漏、无延迟漂移

## 7. ROI 报告

```
## ROI 报告（上线后 N 周）
- 成本节省：原 ____ → 现 ____，月省 ____
- 收入增长：____（来源与口径）
- 质量提升：准确率 __%→__%，客诉 __→__
- ROI：__%
- 隐性成本提示：（培训/变更管理/运维是否已计）
- 结论与建议：（扩量 / 优化 / 终止）
```

```
ROI = (月度人力节省 + 额外收入 − AI 总成本) / AI 总成本 × 100%
月度人力节省 = 原单人耗时×人数×时薪 − 现耗时×人数×时薪 − AI 运营人力
```

三维度必须都算：成本节省 / 收入增长 / 质量提升。陷阱：只算省钱不算挣钱、忽略隐性成本、过度乐观不打折、拿 POC 小样本外推全量。

## 8. 上线前部署验收清单

- [ ] 滚动更新 `maxUnavailable:0 + maxSurge:1`；`readinessProbe.initialDelaySeconds` ≥ 模型加载时间（70B ≥120s）
- [ ] `/dev/shm` ≥16GB（默认 64M 会导致 NCCL 失败）；Pod 反亲和分散到不同主机
- [ ] 模型权重预打包或 init container 预拉取；蓝绿发布需双倍 GPU 资源
- [ ] 金丝雀 5%→25%→50%→100%，每步观察 10–30min
- [ ] Grafana 看板 + AlertManager 规则已生效（TTFT P99、显存、Xid、队列四条必配）
- [ ] 回滚预案：上一版本镜像保留，5 分钟内可 `kubectl rollout undo`
- [ ] 多租户：ResourceQuota + PriorityClass + 按租户限流 + prompt 长度上限
- [ ] 压测用 vLLM benchmark + k6/Locust 端到端实测，不用理论峰值外推

## 9. 填好的样例（照这个密度写，别照这个内容抄）

> 用一个通用的**供应链/物料**场景做示例，说明「填到什么程度算合格」。**数字与场景换你自己的，格式与密度照搬。**
> 本体建模的完整定义见 `references/07-palantir-fde-playbook.md` 第一节。

### 样例 A：需求文档（节选）

```
## 需求文档 v1.2

一、业务背景
物料、采购、库存三套数据分散在 ERP 与两张线下 Excel 里，口径不一致；
缺料预警靠调度员每天的 Excel 宏和经验判断。现在要做，是因为近半年
因缺料导致的产线停线共发生 14 次、平均每次 6 小时。

二、核心痛点（量化）
- 数据分散：物料主数据错漏，ERP 与线下清单对不上的条目约占 8%
- 预警滞后：缺料通常在生产当天才发现，没有提前量
- 无影响面评估：一旦缺料，无法快速判断影响哪些产线、哪些订单
- 当前成本：停线 6 小时 × 14 次/半年，按单位时间产值折算约 ¥42 万

三、功能需求
- Must-have（上线必需）：
  1. 物料/供应商/采购订单/库存四类对象结构化入库
  2. 低于安全库存自动预警（按交期倒排，而不是按当前库存）
  3. 缺料影响面评估：输入一批零件延期，直接列出受影响的产线与订单
  4. 补货单生成后回写 ERP
- Nice-to-have（后续迭代）：
  1. 跨厂区调拨建议与延误成本测算
  2. 供应商交期稳定性评分

四、非功能需求
- 性能：影响面查询 P95 < 3s（20 跳以内链路）；数据同步延迟 ≤ 6h
- 安全：不含个人隐私数据；操作动作需权限校验 + 审计留痕
- 合规：数据不出境；回写 ERP 需双人确认

五、技术约束
- 需与既有 ERP 打通，只读拉取 + 受限回写
- 现有 IT 团队只熟悉 SQL 与 Excel，交付后需能自行维护

六、成功标准（可量化）
- 物料主数据完整率 ≥ 95%，口径统一到单一来源
- 缺料预警提前量 ≥ 交期 − 7 天
- 停线次数：14 次/半年 → ≤ 4 次/半年
- 影响面查询从「人工半天」→ ≤ 3 秒

七、风险与依赖
- 历史数据缺失 → 先接增量，历史数据二期回补
- 供应商交期字段不准 → 先做字段完整性校验，不准的标灰并提示
- 需客户 IT 提供 ERP 只读账号 → 已明确接口人与每周同步机制
```

**注意反面指标的写法**：这个场景**主动排除**了三个指标——「供应链健康度」（不可衡量）、「系统稳定性」（不可操作）、「报表访问量」（虚荣指标）。写需求时说清"不测什么、为什么"，比多列几个指标更专业。

### 样例 B：技术方案 —— 本体建模节选（客户数据乱时先做这段）

```
3. 总体架构设计
   数据层：Ontology 对象/链接存储 + 宽表快照（仅在多表 JOIN 绕不开时用）
   模型层：预警与影响面测算走 Function，不额外引入独立模型服务
   应用层：低代码界面 + 给 IT 预留的查询接口
   集成层：连接器（API / File / DB）+ CDC 增量 + 受限回写 ERP

4. 本体建模（先建模，再接数据源 —— 顺序不可反）
   4.1 核心对象（3–5 个起步，此处列 8 个中的关键项）
       - Material（物料）：sku(自然主键) / name / spec /
         safetyStock(int) / leadTimeDays(int) / status
       - 属性约束：status 用枚举 active/frozen/deprecated，不用裸字符串；
         leadTimeDays 必须为正整数；不能用 Property 表达的才单开对象
       - 反面做法：属性全用裸字符串 → 无法校验、无法枚举、AI 抓不住
   4.2 链接（定基数）
       - materialSuppliedBy：Material → Supplier      （MANY_TO_ONE）
       - poContains：PurchaseOrder → Material         （MANY_TO_MANY，需中间表）
       - inventoryAt：Inventory → Plant               （MANY_TO_ONE）
       - producedOn：Material → ProductionLine        （MANY_TO_ONE）
       - 原则：关系即数据，Link 本身可带属性（权重 / 建立时间）
   4.3 动作（Actions，写操作必须可审计）
       - createPurchaseOrder：参数 (poNo, supplierRid, items[])
         规则：创建订单 + 建 poContains 链接；提交条件：必填 + 数量 > 0
         副作用：通知采购员；参数 ≤ 7 个，超了就拆
       - receiveGoods：收货后回写 ERP（更新库存、改订单状态、触发质检）
   4.4 函数（Functions，只读计算）
       - triggerReplenish：onHand < safetyStock 时生成补货建议
       - assessImpact：输入延期零件批次，按链接链路反查受影响产线与订单
   4.5 最后才接数据源
       - 物料/采购：每天凌晨批量拉取
       - 库存/收货：事件驱动，实时
       - 主数据先做清洗与编码统一，再接上来
```

**这段为什么放在技术方案的第 4 节**：客户数据越乱，越要先做本体（对象/属性/链接/动作），否则等于在脏数据上堆幻觉。**顺序不可反**——先 3–5 个核心对象 → 属性加枚举/正则约束 → 定链接基数 → 定动作 → 最后接数据源。
