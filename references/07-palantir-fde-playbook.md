# 本体建模与现场交付方法论

客户业务说不清、数据又乱的时候，先做本体——把业务抽象成「对象 / 属性 / 链接 / 动作」，AI 才有抓手。本文只留现场能直接用的东西：建模步骤、结构定义、判断标准、部署套路、避坑清单。

---

## 一、Ontology（本体）建模 —— 核心能力

FDE 最独特的能力，是把客户业务抽象成「对象 / 属性 / 链接 / 动作」，再往上搭应用。

**本体不是知识图谱。** 它是用来表达企业决策的**可操作模型**——目的不是「存知识」，而是「驱动行动」。这是它和数仓、图谱最根本的分野。

### 1.1 四个核心概念

| 概念 | 是什么 | 类比 | 关键点 |
|---|---|---|---|
| **Object（对象类型）** | 一类业务实体的数字映射 | 数据库表，但带语义 + 生命周期 | 不是表，是「业务实体 + 生命周期」；单节点可容数亿实例 |
| **Property（属性）** | 对象的带语义字段 | 表的列 | 可追溯（rid 血缘）、可搜索、可展示；用 Value Type 做语义约束 |
| **Link（链接类型）** | 对象之间的关系 | 外键 / JOIN | 是一等公民、双向、可带属性；支持 1:1 / 1:N / M:N / M:1 |
| **Action（动作类型）** | 能对对象执行的操作 | 存储过程 / API | 让模型「改变世界」：参数 → 规则 → 副作用 → 提交条件 |

**判别方法**（先问「这是实体、属性、关系，还是操作」）：

- 客户指着它说「这个东西」→ Object
- 描述它的特征、且不会独立存在 → Property（或 Link）
- 客户会说「A 和 B 之间」→ Link
- 客户会说「我要做 X」→ Action

### 1.2 建模步骤（照着做）

原则：**语义层优先**——先定义 Ontology，再写代码。

1. **识别核心对象**（第 1 天）：从访谈里抓客户反复提到的「名词」。先定 **3–5 个**核心对象，不要一次铺开。
2. **定义属性**：为每个对象列核心属性；用 Value Type 把「定价类型、状态、URL」等做成枚举 / 正则约束，别用裸字符串。
3. **定义链接**：画出对象间关系、定基数（1:1 / 1:N / M:N）。**关系即数据**——Link 本身可带属性（权重、建立时间）。
4. **定义动作**：把客户要「做」的事落成 Action（提交评价、创建订单、触发补货）。
5. **定义计算逻辑**（Function）：排名、热度、评分、推荐这类可复用的计算。
6. **选数据源**（Connectors）：**最后**再接 CRM/ERP/日志，把原始数据映射到对象。
7. **搭应用层**：低代码工具（如 Workshop）快速出界面，复杂需求再上全代码方案（如 Slate）。

做完长什么样：一份 `ontology-manifest`，含 `object-types` / `link-types` / `value-types` / `action-types` / `functions` 目录，业务人员和 AI 都能直接读它。

### 1.3 完整示例：供应链场景（示意）

**对象类型**：`Supplier`（供应商）、`Material`（物料）、`Plant`（工厂）、`PurchaseOrder`（采购订单）、`Inventory`（库存）、`ProductionLine`（产线）、`QualityInspection`（质检记录）、`Shipment`（物流运单）

**属性（节选）**：
- `Material`：`sku`(自然主键)、`name`、`spec`、`safetyStock`(int)、`leadTimeDays`(int)、`status`(ValueType: active/frozen/deprecated)
- `PurchaseOrder`：`poNo`(主键)、`qty`、`unitPrice`、`expectDate`(timestamp)、`status`(ValueType: draft/confirmed/received)
- `Inventory`：`onHand`(int)、`location`(工厂 rid)、`lastCountDate`

**链接**：
- `materialSuppliedBy`：`Material` → `Supplier`（MANY_TO_ONE）
- `poContains`：`PurchaseOrder` → `Material`（MANY_TO_MANY，JOIN_TABLE）
- `inventoryAt`：`Inventory` → `Plant`（MANY_TO_ONE，FOREIGN_KEY）
- `producedOn`：`Material` → `ProductionLine`（MANY_TO_ONE）

**动作（价值所在）**：
- `createPurchaseOrder`：参数 `(poNo, supplierRid, items[])`；规则（创建订单 + 建 `poContains` 链接）；提交条件（必填 + 数量 > 0）；副作用（通知采购员）
- `receiveGoods`（收货回写）：收货后 **Writeback** 回 ERP——更新 `Inventory.onHand`、把 `PurchaseOrder.status` 置为 received、触发 `QualityInspection`。这就是「模型改变世界」
- `triggerReplenish`（自动补货）：当 `Inventory.onHand < safetyStock` 时由 Function 检测并生成补货单

**做完长什么样**：业务人员说「显示所有低于安全库存、且供应商交期 > 7 天的物料」，系统用 Object Set 过滤直接返回语义明确的物料集合，**不用写 SQL JOIN**；点「生成补货单」即触发 Action 并回写 ERP。

### 1.4 三层架构

- **语义层 Semantic Layer**：定义「世界是什么」——Object / Property / Link / Value Type。
- **动力层 Kinetic Layer**：连接现实——Backing Dataset、数据映射、血缘、Sync Engine。
- **动态层 Dynamic Layer**：让数据活起来——Action / Function / Submission Criteria / Writeback。

### 1.5 与数仓、知识图谱的区别（何时用哪个）

| 方案 | 特征 | 何时用 |
|---|---|---|
| 数据仓库 | 静态分析、T+1 批处理 | 只做报表统计，业务人员不直接操作 |
| 知识图谱 | 全量推理、专家构建、更新慢 | 搜索、问答 |
| **Ontology** | 实时、增量、业务人员可直接用 | **客户要的是「能用的操作」而非「能查的知识」** |

## 二、数据工程与 ETL

FDE 在现场 **90% 的部署时间花在数据上**，不是代码上。客户数据永远比想象中乱。

**范式选择**：ETL（先转换后加载）适合传统数仓；ELT（先加载后转换，SQL 即转换）适合云原生，**优先 ELT**。大宽表（OBT，One Big Table）——把相关数据扁平进一张表简化查询，代价是冗余和更新成本，**只在查询确实绕不开多表 JOIN 时才用**。

**脏数据处理四步**：

1. **抓样本**：先拿 100 条脱敏真实数据分析结构，别一上来全量迁移。
2. **建字段映射表**：`{"客户名称": "customer_name", "手机号": "phone"}`，统一 UTF-8（用 `chardet` 探测编码）。
3. **渐进接入**：先跑一天数据再跑全量；先接新数据，历史数据后面再说。
4. **数据质量校验**：导入时校验完整性 / 准确性 / 一致性 / 唯一性 / 有效性（如 `pricingType` 枚举、`rating` 1–5），建质量规则数组 + validate 函数，持续监控。

**集成与血缘**：连接器模式（API / File / DB 抽象类）；变更数据捕获（CDC）按 `updated_at` 拉增量；血缘递归记录「来源 → 目标 → 转换」，出问题能追因。

**性能**：窗口函数（`RANK`/`LAG`/`LEAD`）做排名；CTE 递归查多跳关系；JSONB 操作查 `properties`，GIN 索引加速；`EXPLAIN ANALYZE` 查执行计划。**多跳 Link 查询控制在 20 跳以内。**

**Data as Code**：用 yaml 声明 pipeline（source / transform / sink / quality），可版本化管理。

## 三、AIP / Agent 怎么长在 Ontology 上

LLM 本身只会「说话」；Ontology 给了它**可操作的现实接口**——对象是可查的数据，Action 是可执行的操作，Function 是可调用的计算。没有本体，Agent 只能瞎编。

**三种集成模式**：

1. **本体作为知识库（RAG）**：向量化本体数据，检索后注入 Prompt 生成回答。适用问答 / 推荐。
2. **本体作为工具箱（Tool Use）**：LLM 规划 → 调用 Action / Function → 执行 → 总结。适用复杂工作流自动化。
3. **本体作为记忆（Memory）**：Agent 结果写回本体，后续查询读历史。适用长期学习。

**逻辑编排**：用户输入（自然语言）→ 解析器 → 生成本体查询（Object Set / Function）→ LLM 推理 → 可选执行 Action → 格式化输出。外部 LLM 用模型目录（Model Catalog）统一管理密钥、版本、限流、成本。

**实操要点**：

- Prompt：清晰、结构化、给角色、给约束、Few-shot；复杂任务用 CoT 或 ReAct（Thought → Action → Observation，最多 10 轮）。
- RAG：查询 → 向量化 → topK 检索（带过滤器）→ 拼上下文 → 生成。
- 成本：token 估算约 **1 token ≈ 4 字符**，按日均调用量算日成本，选型时对比各模型单价。
- MLOps：模型生命周期「数据 → 训练 → 评估 → 注册 → 部署 → 监控 → 迭代」；监控延迟（> 2s 告警）、错误率（> 1%）、token 消耗、满意度（< 4.0）；用 KL 散度（> 0.1）做概念漂移检测；A/B 测试定胜负。

## 四、现场交付打法

### 4.1 两周 MVP

原则：**写出能证明「方案可行」的最小代码量，不写一行多余代码。**

**需求捕获五问**：哪里坏了？谁在痛？不修会怎样？修好长什么样？最短路径是什么？

**技术选型**：选最快能跑起来的，不炫技。API 用 FastAPI，数据处理 Pandas + SQLite，前端 Streamlit / Gradio（2 小时出界面），模型用现成 API 或 LangChain。

**三条底线**：① 先让客户说「是」；② 每行代码回答一个问题，答不出就不写；③ 假数据也比没数据好——客户看到「数据进来后的样子」，会自己去整理数据。

**砍掉**：登录 / 权限 / 历史迁移 / 完美 UI。先做一个客户场景，两周一版迭代，不要两个月憋一个完美产品。

### 4.2 最后一公里部署

**客户环境分级**：公有云（★）< 私有云 K8s（★★★）< 物理机房（★★★★）< 断网涉密（★★★★★）。**永远别信「环境已准备好」，带 Plan B。**

**部署三步**：
1. **容器化**：`python:3.11-slim`、`ENV TZ` 定时区、日志走 stdout、加 `HEALTHCHECK`。
2. **IaC**：Docker Compose 覆盖 80% 场景、Terraform 15%、K8s 5%——**不到万不得已别上 K8s**。
3. **上线检查清单**：配置走环境变量、DB 迁移就绪、有健康检查、有告警、有回滚、端口与资源核对。

**CI/CD**：手动部署是敌人。GitHub Actions 一条命令部署；每环境一份配置；**回滚必须比部署快**；部署结果自动通知钉钉 / 微信。

**监控三件套**：Prometheus + Grafana 收集指标与看板 + 钉钉 / 微信告警。必监控 CPU > 80%、内存 > 85%、磁盘 > 85%、P99 延迟 > 3s、5xx > 1%。**无监控 = 裸奔。**

### 4.3 与客户并肩作战

**客户评价你 90% 看体验，10% 看技术。** 把技术翻译成「降本省钱 / 增收赚钱 / 风控不出事」三句话。

**第一次见面黄金 30 分钟**：
- 前 10 分钟聊业务，让客户多说；
- 中 10 分钟展示懂行——「我看了你们数据，发现 X 瓶颈，有类似案例」；
- 后 10 分钟约定配合方式（每天 17 点对进度、建共享决策文档）。

开场直接说：「我今天就是来听你说问题的，你不用懂技术，我负责翻译成方案，结束时给你清晰判断。」

**管理期望**：满意度 = 实际体验 − 期望值。做法是**承诺不足、交付有余**——时间估算按 realistic × 1.2 对外沟通，实际提前完成即超预期。

**需求总变**：通常不是客户的问题，是范围没锁。给客户做选择题——新需求 D 是替换 C、顺延，还是独立立项？

**现场排障节奏**（一小时）：复现 10min → 看日志 / 监控 / 库 10min → 定位根因画图 10min → 出方案 10min → 修复验证 10min → 讲清「为何发生 + 如何避免」10min。常用命令：`tail -100 日志`、`docker logs --tail 100`、`SELECT * FROM pg_stat_activity WHERE state!='idle'`、`dmesg | grep -i oom`。

**撤退**：交付三份文档（操作手册给运营 / 故障手册给运维 / 维护说明给接手人）；核心功能稳定运行 ≥ 2 周、运营能独立操作 ≥ 3 次再撤；做一次 15 分钟毕业复盘，留半年紧急联系方式。**最后印象比第一印象更持久。**

## 五、思维模式与避坑

**几条反过来想会更顺的原则**：

- **对象思维 > 表思维**：从「业务是什么」而非「数据怎么存」出发。看到需求先定义 Object Set，不急着写 SQL。
- **语义层优先**：先本体后代码。反模式是先写码再补本体，必然重构。
- **关系即数据**：Link 是一等公民，双向导航、可带属性。
- **版本与兼容**：新增字段 / 放宽约束 = 安全；删除字段 / 收紧约束 = 危险。渐进迁移：先上新 Schema → 迁数据 → 再废旧 Schema。
- **指标要能打架**：好指标可衡量、可操作、及时、相关、可比较。避免「用户满意度」这种模糊词和「总浏览量」这种虚荣指标。A/B 测试用来**验证**假设而非**确认**偏见——别过早停、别多重比较、别选择性报告。
- **Demo 驱动**：任何阶段都能 2 小时 – 2 天出可跑 Demo，每个 Demo 可丢弃，目的是学习验证。早期亲自替客户整理数据 / 生成报表，等真懂了再自动化。
- **Product 与 FDE 的张力是健康的**：FDE 解当下问题，产品团队建通用能力。管理方式：每周 15 分钟站会、每月 Review「现场的一次性做法能不能升成产品能力」，**FDE 用数据说话而非「我觉得」**。

**五个常见陷阱**：

1. **过度设计本体**：定义 50 个对象，客户只需要 5 个。→ 从 3–5 个核心开始；能用 Property/Link 表达的就不单开对象。对象数建议 **3–20**，再多就是警告信号。
2. **忽视数据质量**：本体完美但数据全空 / 全错。→ 定义质量规则 + 导入时校验 + 持续监控。
3. **Action 过于复杂**：一个 Action 20 个参数、10 步操作。→ 单一职责，**参数 ≤ 7**，复杂流程拆成多个 Action 用工作流组合。
4. **忽视性能直到上线**：开发量小的时候不暴露。→ 用生产级数据量压测、`EXPLAIN` 分析、加缓存、建监控告警。
5. **与客户脱节**：开发 3 个月，客户说「不是我要的」。→ 每日站会 + 每周演示 + 真实用户测试 + 小步快跑。

**沦为咨询的警告信号**：合同金额不增长 / 人员流动率高 / 产品团队不知道你在干什么 / 客户只认人不认产品 / 平台能力不增长 / 团队规模随客户数线性增长。

**对策**：每个项目强制沉淀 ≥ 1 个可复用资产，并建立方法论提取机制。

## 六、什么时候该用 FDE 模式

**适用**：客户问题独特复杂、愿为定制化付费、你能从中提取通用模式、团队具备相应能力、能承受前期投入。

**不适用**：标准化、价格敏感、自助可解决、规模效应明显的场景——那些用 SaaS，不要用 FDE。

**定价思路**：价值定价——卖结果不卖软件（基础费 + 价值分成 + 成功奖励）。健康的标志是**合同金额逐年增长**，不增长即警告信号。

**两个必须平衡的核心指标**：

| 维度 | 指标 |
|---|---|
| 交付结果价值 | 合同金额、续约率、推荐率、NPS |
| 产品杠杆 | 部署时间逐月缩短、人均产出增长、资产复用率、平台功能增长 |

只盯第一个会沦为高价咨询，只盯第二个会脱离客户真实需求。

**启动方式**：避开「Big Launch」陷阱——等完美再发布 = 永远发不出。渐进推进：第 1 周亲自服务 1 个用户 → 第 1 个月服务 5–10 人并快速迭代 → 第 3 个月验证可扩展性 → 第 6 个月平台化。

**团队建设三阶段**：

1. **试点验证**（0–6 月）：1 名 Lead + 2 名 FDE，沉淀 ≥ 3 个可复用组件。
2. **模板化沉淀**（6–18 月）：模板复用率 > 50%，新项目启动时间减半。
3. **平台化运营**（18–36 月）：80% 常见需求可配置，人均产出 ×3。

关键动作：**强制沉淀**（每个项目至少产出 1 个组件 + 1 个模板 + 1 份方法论文档）、知识共享文化、成长可见性。

能力培养分四层：认知层（抽象建模）→ 执行层（拆解执行）→ 表达层（沟通与文档）→ 战略层（价值叙事）。

---

**一句话总结**：FDE = 用本体把客户业务抽象成「对象 / 属性 / 链接 / 动作」→ 接脏数据、做 ELT → 让 AI Agent 长在本体上 → 两周 MVP、容器化部署、与客户并肩作战 → 沉淀可复用资产，别沦为咨询。
