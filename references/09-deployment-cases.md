# 真实部署案例集

三类真实部署过程：70B 模型从 PoC 到生产上线、新模型 1 周上线、GPU 利用率从 40% 提到 75%。全部原始指标数值保留，口径不一致处标 [需确认]。

## 案例 1：70B 模型从 PoC 到生产上线

### 背景

业务需要接入 70B 大模型，支撑智能客服场景。客服场景的特点是请求量集中、回复长度差异大（短问短答与长段解释混在一起），对尾延迟和单请求成本同时敏感。

### 初始方案

用 PyTorch 直接加载模型，两张 A100-80G，FP16。

### 遇到的问题

| 现象 | 根因 |
|------|------|
| 延迟高，P99 = 2.5s | 没有优化，每步都加载全部权重 |
| 显存碎片，batch=16 就 OOM | 连续分配 KV Cache 产生碎片 |
| 吞吐低，只有 30 tok/s/GPU | Static Batching 被长请求阻塞 |
| 成本高，$4000/月/GPU | 利用率只有 35% |

这四个现象不是四件独立的事，而是一条链：没做推理优化 → 每步都加载全部权重 → P99 = 2.5s；KV Cache 连续分配 → 产生碎片 → batch=16 就 OOM → batch 上不去；Static Batching 下同批请求要等最长的那条跑完 → 长请求阻塞整批 → 30 tok/s/GPU；利用率只有 35% → 每张卡每月白付 $4000。

### 优化过程

**Step 1：换 vLLM**
做了什么 → 把 PyTorch 直接加载的推理服务换成 vLLM 承载。
换来什么 → PagedAttention 解决显存碎片，batch 从 16 提升到 128。这是后面所有步骤的前提：batch 上不去，任何调度优化都没空间。

**Step 2：启用 Continuous Batching**
做了什么 → 用连续批处理替代 Static Batching，请求完成即出批、新请求随时入批，不再等整批最长的那条。
换来什么 → GPU 利用率从 35% 提到 70%。

**Step 3：INT8 量化**
做了什么 → 对权重做 INT8 量化。
换来什么 → 显存降一半，batch 还能更大。

**Step 4：建立监控**
做了什么 → 补上利用率、延迟、吞吐的持续监控，而不是上线后靠人肉看。
换来什么 → 发现夜间利用率只有 5%；据此引入弹性缩容，夜间减少实例。这一步不提升单卡性能，但直接作用于月成本。

### 最终结果

| 指标 | 优化前 | 优化后 | 改善 |
|------|--------|--------|------|
| P99 延迟 | 2500ms | 400ms | 6x |
| 吞吐 | 30 tok/s | 100 tok/s | 3x |
| GPU 利用率 | 35% | 75% | 2x |
| 单请求成本 | $0.01 | $0.003 | 3x |
| 月成本 | $32000 | $9600 | 3x |

口径提示：Step 2 记录的利用率是 35%→70%，最终结果表记录 35%→75%，差的 5 个百分点来自后续步骤叠加，具体归属 [需确认]。月成本从 $32000 降到 $9600，同时来自单请求成本下降与夜间缩容两条路径。

### 复盘

- 一开始就该用 vLLM + 量化，而不是自己用 PyTorch 搭推理服务。自研推理栈在这里没有换来任何业务价值，只是把 PagedAttention、Continuous Batching 这些已经成熟的东西重新踩了一遍。
- Profiling 应该更早做。Step 4 才发现夜间利用率只有 5%，这类"钱花在哪"的问题本可以在第一天暴露，结果拖到最后才处理。
- 顺序不能颠倒：先换引擎解决碎片、放开 batch，再量化压显存，最后才动用弹性缩容这类成本手段。前一步的收益是后一步的输入。

## 案例 2：新模型 1 周上线流程

### 背景

DeepSeek 发布新版本，需要在 1 周内部署到测试环境并出评估报告。

### 初始方案（排期）

| 时间 | 内容 |
|------|------|
| Day 1-2 | 信息收集 + 部署：阅读论文和博客；下载模型权重；vLLM 启动，验证能跑通 |
| Day 3-4 | 性能测试：跑标准 benchmark；对比上一版本的性能；测试量化兼容性 |
| Day 5 | 评估报告：性能数据、精度评估；适用场景判断；上线建议 |
| Day 6-7 | 小范围灰度：切 5% 流量测试；监控延迟和错误率 |

### 遇到的问题

| 现象 | 根因 |
|------|------|
| 1 周内要跑完部署、压测、报告、灰度四段 | 排期串行，前面一天的延误直接吃掉后面缓冲 [需确认] |
| 量化兼容性需要单独一轮测试 | 新版本量化是否可用，直接决定上线后的显存与成本 [需确认] |
| 灰度只切 5% 流量 | 需要在真实流量下暴露延迟与错误率，但又不承担全量风险 |
| 具体阻塞点与踩坑记录 | [需确认] |

### 优化过程

**Day 1-2：信息收集 + 部署** → 换来一个能跑通的实例：读完论文与博客拿到版本变化点，下载权重，vLLM 启动并验证能跑通。

**Day 3-4：性能测试** → 换来可对比的结论：跑标准 benchmark，与上一版本逐项对比，并单独测量化兼容性。

**Day 5：评估报告** → 换来决策依据：性能数据、精度评估、适用场景判断、上线建议四件事写进同一份报告。

**Day 6-7：小范围灰度** → 换来真实流量数据：切 5% 流量，监控延迟和错误率。

### 最终结果

| 维度 | 结果 |
|------|------|
| 部署验证 | vLLM 启动，验证能跑通 |
| 性能测试 | 完成标准 benchmark，并与上一版本对比（具体数值 [需确认]） |
| 量化兼容性 | 完成测试（结论 [需确认]） |
| 灰度范围 | 5% 流量，监控延迟和错误率（具体数值 [需确认]） |
| 交付物 | 评估报告：性能数据、精度评估、适用场景判断、上线建议 |
| 总周期 | 1 周（Day 1 到 Day 7） |

### 复盘

- 四段是串行排的，环环相扣却没留缓冲：Day 3-4 的压测一超时，Day 5 的报告和 Day 6-7 的灰度都会被动。更稳的做法是把量化兼容性测试提前到 Day 1-2 与部署并行，因为它只依赖权重、不依赖压测结果。
- 灰度只切 5% 流量是对的，但要先明确"延迟和错误率看哪几个数、超标就回滚"的判定线，否则灰度的 2 天会变成一次没有结论的观察。

## 案例 3：GPU 利用率从 40% 提到 75%

### 背景

线上推理服务 GPU 利用率长期只有 40%，成本浪费严重。

### 初始方案

线上已有一套推理服务在跑，GPU 利用率长期停在 40%。第一步不是改配置，而是先确认这个 40% 是不是看错了。

### 遇到的问题

| 现象 | 根因 |
|------|------|
| nvidia-smi 显示 GPU 利用率确实低，只有 40% | 未定位，需进一步 profile |
| nsys profile：30% 时间在等 CPU 发请求 | CPU 处理慢（JSON 解析 + tokenization）→ GPU 等数据 |
| nsys profile：40% 时间在 decode | 正常解码开销 |
| nsys profile：30% 时间 GPU 闲置（batch 不满） | 请求量不够，batch 经常不满 → 实例过多 |

这里的关键是把一个笼统的"利用率 40%"拆成三段：30% 在等 CPU、40% 在 decode、30% 在闲置。40% 的 decode 是干活的，真正要治的是另外 60%——而它们对应两组完全不同的动作。

### 优化过程

**Step 0：profiling**
做了什么 → 先用 nvidia-smi 确认利用率低，再用 nsys profile 把时间拆到 30% 等 CPU / 40% decode / 30% GPU 闲置。
换来什么 → 得到两个可操作的根因：请求量不够导致 batch 经常不满、实例过多；CPU 处理慢（JSON 解析 + tokenization）导致 GPU 等数据。

**Step 1：减少实例数，提高单实例 batch**
做了什么 → 把分散在多实例上的请求收拢，让单实例的 batch 更容易填满。
换来什么 → 利用率 +15%。

**Step 2：CPU 侧用多线程预处理**
做了什么 → 把 JSON 解析 + tokenization 的串行处理改成多线程。
换来什么 → 利用率 +10%。

**Step 3：引入前缀缓存**
做了什么 → 对重复前缀做缓存复用。
换来什么 → 利用率 +10%。

**Step 4：合并短回复请求**
做了什么 → 把短回复请求合并成批处理。
换来什么 → 利用率 +5%。

### 最终结果

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| GPU 利用率 | 40% | 75% | +35 个百分点 |
| 成本 | 基准 | 降低约 40% | 约 40% |

逐项贡献：减少实例数 / 提高单实例 batch +15%；CPU 多线程预处理 +10%；前缀缓存 +10%；合并短回复请求 +5%。四项合计 +40 个百分点，与 40%→75% 的 +35 个百分点存在差值，口径（相对提升或未全部叠加）[需确认]。

### 复盘

- 先 profile 再动手。nvidia-smi 只能告诉你"利用率低"，nsys 才能告诉你"低在哪"。三段时间分别指向 CPU 预处理、decode、batch 不满，对应的是三组完全不同的动作；没有这一步，很容易一上来就加卡或换模型。
- 利用率低不等于算力不够。本例 60% 的时间既不在算也在闲置：30% 是 GPU 在等 CPU 喂数据，30% 是 batch 填不满。这两件事都不是买更多卡能解决的。
- 优先做低成本项。CPU 多线程预处理、前缀缓存、合并短回复请求，都不改模型、不动精度，收益却是实打实的。
- 减少实例数的代价要盯住：单实例 batch 抬高后，批里长短请求的相互等待会变多，尾延迟需要重新测一轮 [需确认]。

## 这些案例的共性结论

1. **先上成熟推理引擎，再谈自研。** 案例 1 从 P99 2500ms → 400ms（6x）、吞吐 30 → 100 tok/s（3x），起点只是换成 vLLM：PagedAttention 解决碎片让 batch 从 16 到 128，Continuous Batching 把利用率从 35% 提到 70%。自研推理栈在这里只重复了已有工作，没换来业务价值。
2. **Profiling 要早做，而且要做到系统层。** 案例 1 到 Step 4 建立监控才发现夜间利用率只有 5%；案例 3 靠 nsys 才把笼统的 40% 拆成 30% 等 CPU / 40% decode / 30% 闲置。晚做 profiling 的代价，是把本来第一天就能暴露的成本问题拖到最后。
3. **瓶颈通常不在 GPU 算力，而在喂不满和等数据。** 案例 3 里 60% 的非解码时间，一半是 GPU 等 CPU 做 JSON 解析 + tokenization，一半是请求量不够导致 batch 不满；案例 1 则被 Static Batching 的长请求阻塞。加卡解决不了这两类问题。
4. **优化有先后顺序，且每步为下一步腾空间。** 先解决显存与 batch 天花板（换引擎 / 量化），再压精度（INT8 显存降一半），最后才动用弹性缩容这类成本手段——案例 1 的 $32000 → $9600 是这条链叠加的结果。
5. **上线要保留同一套指标口径，并把灰度判定线先写下来。** 延迟（P99）、吞吐（tok/s）、利用率（%）、单请求成本（$/请求）四项必须前后可比，否则无法判断优化是否真的生效；案例 2 的灰度切 5% 流量，前提是先定好延迟与错误率的回滚线。
