# FDE 客户现场工作流（Skill 核心骨架）

> 适用对象：在企业客户现场执行 AI 落地交付的前沿部署工程师（FDE）。
> 本文定义「进门之后干什么、按什么顺序、每步交付什么」，是所有交付动作的单一事实来源。
> 配套模块：客户画像 / 需求拆解 / 方案生成 / 竞品对比 / 话术准备 / POC 设计 / 交付上线 / ROI 度量 / 推广扩量。

---

## 〇、总览：九步工作流与交接关系

| 步骤 | 名称 | 上游输入 | 本步交付物 | 下游交接 |
|---|---|---|---|---|
| 1 | 客户画像 | 客户基础信息、行业、初次接触记录 | 客户画像卡 | → 需求拆解 |
| 2 | 需求拆解 | 客户画像卡 + 访谈记录 | 结构化需求文档 | → 方案生成 |
| 3 | 方案生成 | 结构化需求文档 | 技术方案 + 实施路线图 | → 竞品对比 / 话术准备 |
| 4 | 竞品对比 | 方案要点 + 客户关注维度 | 竞品对比表 + 差异化话术 | → 话术准备 |
| 5 | 话术准备 | 方案 + 竞品对比 + 客户决策链 | 分角色话术包 | → POC 设计 / 商务推进 |
| 6 | POC 设计 | 需求文档 + 成功标准 | POC 方案 + 验收标准 | → 交付上线 |
| 7 | 交付上线 | POC 验证结果 + 生产环境就绪 | 灰度上线报告 + 运行基线 | → ROI 度量 |
| 8 | ROI 度量 | 运行数据 + 业务指标 | ROI 报告 + 复盘 | → 推广扩量 |
| 9 | 推广扩量 | ROI 验证 + 标杆案例 | 扩量计划 + 采纳运营机制 | → 持续运营 |

**核心原则**
- 先对齐再动手：任何一步的「完成标准」未达成，不进入下一步。
- 需求文档是合同性文件：后续方案、POC、验收全部以它为准，变更必须走变更新增。
- 全程记录审计线索：每次关键决策留痕（谁、何时、依据哪份文档、结论是什么）。
- 安全与合规是红线，不是可选项，嵌入每一步（见第六节）。

## 一、客户画像（谁是我客户）

**输入**：客户名称、行业、规模、初次接触纪要、公开信息（官网/年报/新闻）。
**动作**：
1. 归纳行业特征与共性痛点（用行业模板，不要凭空编）。
2. 列出 3–6 个典型业务场景（高价值、高频、当前痛点明显）。
3. 评估技术成熟度：数据基础、既有系统、IT 能力、AI 接受度。
4. 画出决策链：谁拍板、谁影响、谁使用、谁埋单。
5. 检索历史同类客户案例，作为参照与信任背书。

**输出（可直接填充的模板）**：
```
## 客户画像卡
- 客户名称 / 行业 / 规模：
- 行业特征与共性痛点：
  1.
  2.
- 典型业务场景（按价值排序）：
  | 场景 | 频率 | 当前痛点 | 潜在价值 |
  |---|---|---|---|
  |  |  |  |  |
- 技术成熟度评估：
  - 数据基础（有无标注/知识库）：
  - 既有系统（CRM/ERP/MES…）：
  - IT 与 AI 能力：
  - AI 接受度（保守/中性/激进）：
- 决策链分析：
  | 角色 | 姓名/职级 | 关注点 | 影响力 | 我方对接策略 |
  |---|---|---|---|---|
  | CTO |  |  | 高/中/低 |  |
  | 业务负责人 |  |  |  |  |
  | 采购 |  |  |  |  |
  | 一线使用者 |  |  |  |  |
- 历史同类案例推荐：
```

**完成标准**：决策链中每个角色有关注点与对接策略；至少 1 个可引用的同类案例；场景已排序。

## 二、需求拆解（把含糊的话变成可验收的需求）

**输入**：客户画像卡 + 访谈/会议记录 + 客户随口提的诉求。
**动作（先宽后窄，多轮对话）**：
- 第一轮问业务目标：「你最终想解决什么业务问题、达成什么指标？」而非直接问技术参数。
- 逐步收窄：「响应时间要求多少？」「现在谁在做、每天耗时多少？」「出错代价多大？」
- 资料建议 5–8 轮澄清对话，直到 Must-have 与 Nice-to-have 分清。
- 识别伪需求与不可行需求（见下）。

**输出模板（合同性文件，7 节）**：
```
## 需求文档 vX.Y
一、业务背景：（客户为什么现在要做这件事）
二、核心痛点：（量化，如「每单人工审核 8 分钟，日 2000 单」）
三、功能需求：
  - Must-have（上线必需）：
    1.
  - Nice-to-have（后续迭代）：
    1.
四、非功能需求：
  - 性能（吞吐/延迟/并发）：
  - 安全（加密/权限/审计）：
  - 合规（数据出境/PIPL/行业监管）：
五、技术约束：（既有系统、网络、私有化要求、语言）
六、成功标准：（可量化、可测量，如「人工审核占比从 100% 降至 ≤30%」）
七、风险与依赖：（缺数据？需客户 IT 配合？决策人未对齐？）
```

**补全需求的反问清单（逐条确认，缺则补齐）**：
- [ ] 业务目标是否可量化？不可量化则要求客户给基线数字。
- [ ] 当前由谁、用什么方式完成？耗时/成本/错误率基线是多少？
- [ ] 峰值与常态负载分别是多少？
- [ ] 数据从哪来、是否可授权使用、是否含 PII（见第六节）？
- [ ] 失败/错误的业务代价与兜底要求？
- [ ] 上线后谁来运营、有无 IT 接口人？
- [ ] 决策人与预算是否明确？
- [ ] 是否有竞品已在做、客户对之满意度如何？

**识别伪需求 / 不可行需求（红黄牌）**：
- 🚩 伪需求：用 AI 包装旧系统短板（如「用大模型补 ERP 数据质量」其实是流程问题）；把 KPI 当需求（「要 AI 替代人」但无场景）。
- 🚩 不可行：要求 100% 准确且无人工兜底（LLM 固有不确定性）；要求实时但数据 T+1；要求私有化但零算力预算；要求模型「永远不犯错」且零误杀。
- 处理：当场指出并给替代路径；若客户坚持，写入「风险与依赖」并请其签字确认范围，不背不可能实现的指标。

**需求拆解实操示例（制造业 AI 质检）**：
```
客户原话：「我们质检太慢了，想用 AI 搞一下。」
第1轮（宽）：你最终想解决什么？→「漏检导致客诉退货，每月赔不少。」
第2轮（窄）：现在谁检、怎么检？→「终检 12 人，每件看 30 秒，日 8000 件。」
第3轮：漏检率现在多少？→「约 3%，客诉月 40 单，赔 ¥15 万。」
第4轮：AI 接哪？→「产线相机已有权图，但要实时，延时 < 200ms。」
第5轮：误杀代价？→「误杀最多复检，可接受，但漏检零容忍偏高优先。」
→ 落成需求：Must-have=实时缺陷识别、漏检率 ≤0.5%、延时<200ms、误杀可复检；
  Nice-to-have=自动分类缺陷类型、生成质检报表。成功标准=漏检率 3%→≤0.5%。
```

**完成标准**：7 节齐全；Must/Nice 分开；成功标准可量化；伪/不可行需求已处理并留痕。

## 三、方案生成（给客户一张可信的图）

**输入**：结构化需求文档。
**动作**：
1. 现状分析与痛点诊断（呼应需求第二节）。
2. 总体架构设计：数据层 / 模型层 / 应用层 / 集成层。
3. 技术方案详述：选型（自研/开源/商用）、RAG 还是微调、Agent 编排方式。
4. 实施路线图（分阶段、有里程碑）。
5. 预期效果与 ROI 初估（见第八节公式）。

**输出模板（9 节）**：
```
## 技术方案
1. 项目概述：（一句话目标 + 范围）
2. 现状分析与痛点诊断：
3. 总体架构设计：（附架构图占位）
   - 数据层：
   - 模型层：
   - 应用层：
   - 集成层（与 CRM/ERP 对接）：
4. 技术方案详述：
   - 数据接入与知识库（ChromaDB 等行业/案例/话术集合）：
   - 模型与推理（部署形态：云/私有化/混合）：
   - 应用与交互：
   - 集成与 Webhook（HMAC 校验、CloudEvents、指数退避重试）：
5. 产品选型建议：（含理由与备选）
6. 实施路线图：（M1 数据准备 / M2 POC / M3 灰度 / M4 扩量）
7. 预期效果与 ROI：
8. 风险与应对：
9. 附录：（术语、参考案例）
```

**架构决策提示**：
- 不确定性高的环节用 Human-in-the-Loop（HITL）：预审 / 后置审批 / 抽检三模式。
- 置信度路由：≥0.9 自动处理；0.7–0.9 人工复核；<0.7 人工处理。超时 30s 降级到人工。
- 集成必须带鉴权与重试（指数退避），跨服务用 Saga 补偿避免半成品状态。

**完成标准**：架构四层清晰；实施路线图有里程碑；ROI 有初估；风险有应对。

## 四、竞品对比（客户为什么选我们）

**输入**：方案要点 + 客户明示/暗示的关注维度。
**动作**：按客户最在意的 3–4 个维度做对比，不堆全维度。给差异化话术（见第五节）。

**输出模板**：
```
## 竞品对比
对比维度（按客户关注排序）：技术架构 / 功能覆盖 / 性能 / 价格模式 / 服务支持 / 口碑
| 维度 | 我方 | 竞品A | 竞品B | 客户权重 |
|---|---|---|---|---|
| 技术架构 |  |  |  | 高 |
| 功能覆盖度 |  |  |  | 中 |
| 性能（延迟/准确） |  |  |  | 高 |
| 价格模式 |  |  |  | 中 |
| 服务支持 |  |  |  | 低 |
| 客户口碑 |  |  |  | 低 |
差异化小结：（我们强在哪、弱在哪、弱项如何补）
```

**完成标准**：维度按客户权重排序；差异化小结客观（不抹黑竞品，不夸大自己）。

## 五、话术准备（分角色讲人话）

**输入**：方案 + 竞品对比 + 客户决策链。
**动作**：为每条决策链角色准备对应话术，核心是「切换视角，讲对方在乎的」。

**分角色沟通要点**：

| 角色 | 最关心 | 话术切入 | 要避免 |
|---|---|---|---|
| CTO / 技术负责人 | 架构合理性、可维护性、安全合规、集成成本 | 「这套架构如何融入你现有体系、如何降级、如何审计」 | 只谈业务价值不谈技术细节 |
| 业务负责人 | 效果、ROI、多久见效、对 KPI 的贡献 | 「上线后你的指标怎么变、3 个月看到什么」 | 堆技术名词 |
| 采购 / 商务 | 总成本、合规风险、供应商风险、退出机制 | 「TCO 构成、数据归属、SLA 与赔付」 | 只讲技术先进 |
| 一线使用者 | 好不好用、会不会增加负担、会不会替代我 | 「怎么嵌入你现有工作流、帮你减负、你仍把关」 | 让人感觉要被替代 |

**话术类型库（可直接套）**：
- 开场破冰：共情行业痛点 + 一句价值主张。
- 需求探询：用第二节反问清单，多问少讲。
- 方案呈现：先结论（业务效果）后支撑（架构），配 1 张图。
- 异议处理：认同→数据/案例回应→给出让步或兜底（如 HITL 降级）。
- 成交推进：明确下一步（POC 范围/时间/双方责任），要承诺。

**完成标准**：决策链每个角色有专属话术；异议处理有兜底方案；下一步动作被客户确认。

**分角色话术示例（可直接改姓名套用）**：
- 对 CTO：「张总，架构上我们复用你现有 CRM 的账号体系，模型私有化部署在你的机房，所有推理留审计日志可回放，异常一键回退到规则引擎——不碰你核心数据，也不绑架你技术栈。」
- 对业务负责人：「李总，按你现在 12 人终检、日 8000 件算，上线后预计人工降到 2 人监管，漏检率从 3% 压到 0.5%，按月客诉赔款 ¥15 万基本归零，三个月你能看到这条曲线。」
- 对采购：「王经理，TCO 是一次性部署 + 按年订阅，数据归属你方，合同含 SLA 与未达标赔付，到期可平滑导出迁移，不存在锁定。」
- 对一线使用者：「陈工，系统不是取代你，是把最累的『盯屏幕找划痕』交给它，你只复核它拿不准的 20%，工作量少一大半，终审权还在你手里。」

## 六、合规与安全红线（嵌入每一步，不可妥协）

**数据分级（PII 三级）**：
- 直接标识符：姓名、身份证、手机号、人脸。→ 默认不采集、不进模型、必须脱敏。
- 间接标识符：邮箱、地址、设备号。→ 假名化/脱敏后可用。
- 准标识符组合：年龄+性别+邮编等可再识别。→ 做 k-匿名化处理。

**六条红线（触碰任一条立即停止并上报）**：
1. 🚩 原始 PII 不得进入训练集、提示词或日志原文。审计日志只存 `input_summary` / `output_summary` + `prompt_hash`，不存明文 PII。
2. 🚩 个人信息境内存储（PIPL）：出境需单独同意 + 安全评估；未获批不传境外。
3. 🚩 最小必要原则：只取完成任务所需字段，不囤数据。
4. 🚩 Prompt 注入防御（OWASP LLM01）：直接注入 / 间接注入 / Token 逃逸三类。五层防御：输入清洗 → 权限隔离 → 工具调用白名单 → 输出校验 → 行为监控。上线前红队测试（Garak / PyRIT）。
5. 🚩 可审计可解释：每次推理留 `request_id / timestamp / model_version / prompt_hash / 置信度 / 人工是否介入`；WORM 存储，金融类保留 7 年。
6. 🚩 模型版本可回滚：上线即锁版本，异常一键回退到规则引擎或人工。

**安全自检清单（每步交付前勾）**：
- [ ] 是否含 PII？含则已脱敏/假名化，且客户已授权。
- [ ] 数据是否出境？是则已走合规审批。
- [ ] 提示词/工具调用是否做了注入防护？
- [ ] 审计日志字段是否齐全且不含明文 PII？
- [ ] 模型版本是否锁定、可否回滚？
- [ ] 失败降级路径是否定义（备用模型→规则引擎→转人工）？

**完成标准**：六条红线逐条核查通过；自检清单全勾；不合规项已上报未私自绕过。

## 七、POC 设计（用小成本证明价值）

**输入**：需求文档（成功标准）+ 客户可提供的资源。
**动作**：把「成功标准」翻译成可测的 POC 验收线，限定范围、定周期、定双方责任。

**POC 方案模板**：
```
## POC 方案
- POC 目标与成功标准：（量化，如「在 200 条样本上准确率 ≥85%，人工复核 ≤30%」）
- 测试场景设计：（2–4 个代表场景，覆盖边界与常态）
- 数据准备方案：（样本来源、规模、脱敏要求、客户提供时限）
- 环境搭建要求：（网络/算力/账号/接口人）
- 实施周期与里程碑：（建议 2–4 周；M1 数据就绪 / M2 跑通 / M3 验收）
- 验收标准：（明确指标 + 测量方法 + 谁认定通过）
- 风险预案：（数据不到位 / 指标不达标 / 客户无人力 的应对）
- 双方责任：我方 ____ ；客户方 ____ （签字）
```

**量化成功标准写法**：
- 错：「效果明显提升」。对：「人工审核占比从 100% 降至 ≤30%，单均耗时 8min→≤2min」。
- 错：「准确率够用」。对：「在 200 条标注样本上 F1 ≥ 0.85，误杀率 ≤ 1%」。

**常见 POC 失败原因（提前规避）**：
1. 范围无限膨胀：客户中途加需求 → 用需求文档锁范围，新增走变更。
2. 数据不到位：客户迟迟不给样本 → POC 方案写明数据时限与违约后果。
3. 成功标准先松后紧：验收时客户改口径 → 验收标准双方签字，不接受口头变更。
4. 没有业务基线：无法证明提升 → 先用客户现有方式跑一批基线数字。
5. 客户无人配合：变成我方自嗨 → 明确客户接口人与每周同步机制。

**完成标准**：目标可量化、周期明确、责任签字；验收标准双方书面确认。

**POC 设计实操示例（接上质检场景）**：
```
POC 目标：在客户提供的 500 张标注图（含 50 张缺陷图）上验证漏检率 ≤0.5%、延时<200ms。
测试场景：① 常态良品（400 张）② 常见划痕（30 张）③ 低对比度缺陷（20 张，边界）④ 反光干扰（50 张，干扰）
数据准备：客户 3 个工作日内提供脱敏后图（不含量号 PII），我方标注复核。
环境：客户内网 GPU 服务器 1 台，我方远程只读部署。
周期：3 周（W1 数据/M2 跑通/M3 验收），每周五同步。
验收：漏检率≤0.5% 且 误杀率≤5% 且 P95 延时<200ms，三方签字通过。
风险预案：数据迟交→顺延并书报；指标不达标→定位是数据还是模型，给优化排期不强行通过。
```

## 八、交付上线与 ROI 度量（证明并放大价值）

### 8.1 灰度上线三阶段
- 阶段一 人工辅助 AI（自动率 20–40%）：AI 建议、人把关，建立信任。
- 阶段二 部分自动化（60–80%）：常规走自动，低置信转人工。
- 阶段三 全自动化（90%+）：仅异常人工介入，配监控告警。

**上线输入**：POC 验证通过 + 生产环境就绪 + 安全自检全勾。
**输出**：灰度报告（各阶段自动率、准确率、人工介入量）+ 运行基线。

### 8.2 ROI 度量（三维度）
- 成本节省：人力/运维/错误成本下降。
- 收入增长：转化提升、客单提升、新场景增收。
- 质量提升：准确率、合规率、客户满意度。

**ROI 公式**：
```
ROI = (月度人力节省 + 额外收入 - AI 总成本) / AI 总成本 × 100%
月度人力节省 = 原单人耗时×人数×时薪 − 现耗时×人数×时薪 − AI 运营人力
```
示例：原 10 人×8h×¥80=¥6.4K/日 → AI 后 2 人×2h 监管=¥0.32K/日，月省约 ¥180K（按 22 天），净节省扣 AI 成本后为正即成立。

**ROI 报告模板**：
```
## ROI 报告（上线后 N 周）
- 成本节省：原 ____ → 现 ____，月省 ____
- 收入增长：____（来源与口径）
- 质量提升：准确率 __%→__%，客诉 __→__
- ROI：__%（公式与取值见上）
- 隐性成本提示：（培训/变更管理/运维是否已计）
- 结论与建议：（扩量 / 优化 / 终止）
```

**常见 ROI 陷阱**：只算成本不算收入；忽略隐性成本（培训、运维）；过度乐观不打折；用 POC 小样本外推全量。

### 8.3 推广扩量（让价值长出来）
采纳生命周期：Aware（知道）→ Trust（信）→ Adopt（用）→ Depend（离不开）→ Advocate（帮推）。
- 培训金字塔 L1 认知 / L2 操作 / L3 排障 / L4 优化，对应不同角色。
- 扩量节奏：单场景验证 → 同部门复制 → 跨场景 → 跨业务线。每扩一层重复 ROI 度量。
- 标杆案例沉淀：STAR 法（背景/挑战/方案/结果/复盘），量化指标对外可讲。

**完成标准**：三阶段灰度有据；ROI 报告含三维度与公式；扩量计划与采纳运营机制就绪。

**ROI 度量实操示例（质检场景，月度）**：
```
原：12 人 × 8h × ¥80/h × 22 天 = ¥168,960/月 人力
现：2 人监管 × 8h × ¥80 × 22 = ¥28,160 + AI 订阅/算力 ¥20,000 = ¥48,160
月省人力：¥120,800；客诉赔款归零 +¥15,000 等效收益
月总收益：¥135,800；AI 总成本：¥20,000
ROI = (135,800 − 20,000) / 20,000 × 100% = 579%
隐性成本已计：培训 1 次 ¥0（内部）、运维 0.2 人月已含在监管人力
结论：达标，建议复制到第二条产线（扩量）。
```

## 九、变革采纳与阻力应对（70% AI 项目死在「没人用」）

**失败主因占比参考**：缺乏信任 35% / 流程不匹配 25% / 技能缺口 15% / 恐惧被替代 12% / 指标不清晰 8% / 技术故障 5%。
**动作**：
- 信任：先人工辅助阶段让使用者看到 AI 帮他减负，而非替代。
- 流程匹配：把 AI 嵌进现有工作流，不要求人改习惯迁就系统。
- 技能：分层培训 + 一页操作卡 + 内部答疑群。
- 恐惧：明确「人仍把关、AI 做重复活」，用数据证明工作量下降。

**阻力应对表**：
| 阻力 | 信号 | 应对 |
|---|---|---|
| 不信任 | 结果被无视、仍全人工 | 小胜快交付 + 透明可解释 |
| 流程不符 | 系统外另走一套 | 重新映射工作流节点 |
| 技能缺 | 操作卡壳、报错多 | L2 实操培训 + 答疑 |
| 被替代焦虑 | 抵触、消极使用 | 强调减负与把关角色 |

**降级层级（保可用）**：备用模型 → 规则引擎 → 转人工，配合置信度阈值与监控。

**完成标准**：已识别主要阻力并有应对；培训与答疑机制落地；降级路径可用。

## 十、最常见坑与应对（FDE 现场急救包）

| 坑 | 表现 | 应对 |
|---|---|---|
| 需求没对齐 | 方案做完客户说「不是我要的」 | 第二节 7 节需求文档签字； Must/Nice 分清；反问清单补全 |
| POC 成了但上不了线 | 演示惊艳，生产无跟进 | POC 方案即含上线责任与数据/接口承诺；阶段一灰度从 POC 结束即启动 |
| 客户方没人配合 | 数据/账号/会议全拖 | 合同写接口人与 SLA；高层对齐决策人；无配合则暂停并书面风险报备 |
| 范围蔓延 | 中途不断加需求 | 需求文档锁范围；新增走变更单与排期 |
| 指标被改口 | 验收时提高标准 | 验收标准双方签字，不接受口头变更 |
| 合规踩线 | 客户要求传 PII 出境/进模型 | 第六节红线，触碰即停并上报，给合规替代方案 |
| 没人用 | 上线后使用率掉 | 第九节采纳机制；先减负再扩量 |
| 只算省钱不算挣钱 | ROI 被质疑 | 三维度 + 公式；隐性成本计入 |
